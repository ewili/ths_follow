# User Story — 提问驱动的需求澄清与用户故事创建

**核心原则：先理解，再书写。** 不根据用户第一句描述直接输出用户故事，而是通过多轮提问挖掘真实需求，最后结合项目代码分析生成文档。

## 触发条件

- 用户要求"创建用户故事"/"新需求"/"我想加个功能"/"user story"
- 用户描述了一个模糊的功能想法
- 用户想对现有功能做改动但不清楚细节

## 全流程

```
Phase 1: 需求初听 → 复述确认（1 轮）
Phase 2: 深度追问 → 逐层展开（2-5 轮）
Phase 3: 代码探查 → 架构适配（1 轮，Agent 自主完成）
Phase 4: 生成文档 → 用户确认（1-2 轮）
```

---

## Phase 1: 复述确认

**目标**：确保 Agent 正确理解用户表述，不急于展开。

操作：
1. 用自己的话复述用户需求，标注理解与不确定之处
2. 提出 2-3 个澄清性问题（从下方问题库选取最相关的）
3. **停止**，等待用户回答

输出格式：
```
## 我的理解
[用自己的话复述需求]

## 需要澄清
1. [问题1]
2. [问题2]
3. [问题3]
```

---

## Phase 2: 深度追问

**目标**：逐层挖掘，直到用户故事六要素（Who/What/Why/Acceptance/Edge/Constraint）基本清晰。

**追问策略**：每次最多提 3 个问题，围绕同一个维度深挖，不要跳跃。

### 问题维度与典型问题

| 维度 | 典型问题 |
|------|----------|
| **角色(Who)** | 这个功能谁用？喊单端还是跟单端？还是两端都要？ |
| **场景(When)** | 什么时候触发？交易时段？手动触发？定时？ |
| **行为(What)** | 具体操作什么？输入什么、输出什么？看到什么变化？ |
| **目的(Why)** | 为什么需要？解决什么痛点？不用会怎样？ |
| **边界(Edge)** | 极端情况怎么处理？网络断了？数据为空？并发冲突？ |
| **约束(Constraint)** | 有无性能要求？延迟容忍度？必须兼容现有 API？ |

### 追问判断标准

继续追问的条件（满足任一即继续）：
- 用户回答仍模糊（"大概"/"可能"/"随便"）
- 尚未明确角色（哪个端）
- 尚未明确核心操作（CRUD 哪个）
- 尚未考虑边界情况
- 需求涉及跨端改动但用户只提了一端

停止追问的条件（满足全部即停止）：
- 用户故事六要素已有初步答案
- 用户表示"差不多了"/"就这样"/"你看着定"
- 提问已超过 5 轮

---

## Phase 3: 代码探查

**目标**：深入项目代码，理解现有架构，确保用户故事的技术方案贴合项目实际情况。

**此阶段 Agent 自主完成，不打扰用户。**

必须执行的操作：

1. **定位相关模块**：根据需求涉及的功能领域，用 `codebase_search` 找到相关代码
2. **阅读核心文件**：完整阅读涉及的 API 路由、Service、Model、前端组件
3. **梳理数据流**：从前端 → API → Service → DB/外部 的完整链路
4. **识别影响面**：标注需要新增/修改的文件列表
5. **检查现有约定**：命名风格、错误处理模式、缓存策略、单例模式等

探查清单：
```
- [ ] 相关 API 路由文件已阅读
- [ ] 相关 Service 层已阅读
- [ ] 相关 Model/Schema 已阅读
- [ ] 相关前端组件已阅读（如涉及）
- [ ] 数据库 schema 已查看（如涉及）
- [ ] 配置项已查看（如涉及）
```

### 项目架构速查

| 端 | 目录 | 说明 |
|----|------|------|
| 喊单 | `signal-server/app/` | FastAPI + SQLite + easytrader |
| 跟单 | `follow-client/app/` | FastAPI + SQLite + easytrader |

每端结构：
```
app/
├── api/        # FastAPI 路由（按功能分文件）
├── core/       # 配置、日志、时段守卫
├── db/         # SQLite 仓库层 + schema.sql
├── models/     # Pydantic 请求/响应模型
├── services/   # 业务逻辑（单例模式）
├── tasks/      # 定时任务（仅 signal-server）
└── utils/      # easytrader 补丁、THS GUI 交互
```

API 前缀速查（勿混淆）：

| 端 | 前缀 | 持仓 | 委托 | 资金 |
|----|------|------|------|------|
| 喊单 | `/api/signal` | `/positions` | `/entrusts` | `/balance` |
| 跟单 | `/api/trader` | `/positions` | `/entrusts` | `/balance` |
| 跟单引擎 | `/api/follow` | — | — | — |

注意：跟单端前缀是 `/api/trader` 而非 `/api/follow`；持仓和委托路径是复数。

## Phase 4: 生成文档

**目标**：基于前三个阶段的成果，输出完整的用户故事文档。

1. 按模板生成用户故事文档（见 [user-story-template.md](user-story-template.md)）
2. 文档存放在 `.cursor/skills/user-story/` 目录，文件名格式 `US-{NNN}-{short-name}.md`
3. 编号从现有文件最大编号 +1 开始
4. **先输出文档让用户确认**，确认后才写入文件

### 文档确认要点

向用户确认：
- 用户故事描述是否准确
- 验收标准是否完整
- 技术方案是否合理
- 影响范围是否有遗漏

用户确认后写入文件；用户要求修改则更新后再次确认。

---

## 原则

1. **提问优先**：宁多问一轮，不猜测用户意图
2. **渐进收敛**：从模糊到具体，每轮缩小不确定性
3. **代码为证**：技术方案必须基于实际代码分析，不凭空设计
4. **架构一致**：新增功能遵循现有模式（单例 Service、with_lock、TTL 缓存等）
5. **双端意识**：任何需求先判断涉及哪一端或双端，双端改动标注同步要求
6. **边界必问**：每个用户故事必须考虑异常/边界场景
