# Plan Mode — 先规划再执行

进入规划模式时，Agent **只做分析和规划，不执行任何代码修改**。输出一份结构化计划，等待用户确认后再实施。

## 触发条件

- 用户明确要求"规划"/"plan"/"先别改"/"帮我分析一下"
- 任务涉及 3 个以上文件的修改
- 任务涉及架构变更、新增模块、跨端同步等高风险操作
- 用户要求先看方案再决定

## 规划流程

### Phase 1: 信息收集

1. **读取相关文件**：定位所有涉及的源文件，完整阅读，不猜测内容
2. **理解现有架构**：梳理模块依赖、数据流、接口契约
3. **识别约束条件**：项目规则、现有约定、兼容性要求

### Phase 2: 分析与设计

1. **问题拆解**：将大任务拆成独立、可排序的子任务
2. **依赖关系**：标明子任务之间的前后依赖
3. **影响范围**：每个子任务涉及的文件列表和影响面
4. **风险评估**：标注可能出问题的环节（如跨端同步、时序竞争、数据迁移等）

### Phase 3: 输出计划

按以下模板输出：

```markdown
# 📋 执行计划

## 目标
[一句话描述本次变更的目标]

## 现状分析
- 当前架构/逻辑简述
- 需要解决的问题

## 执行步骤

### Step 1: [子任务名称]
- **操作**: [具体做什么]
- **涉及文件**: `path/to/file1.py`, `path/to/file2.py`
- **影响范围**: [描述]
- **风险**: [无/低/中/高] — [说明]
- **依赖**: 无 / 依赖 Step N

### Step 2: [子任务名称]
...

## 不在本次范围
- [明确排除的内容，避免范围蔓延]

## 验证方案
- [如何确认每步正确]
- [最终验收标准]
```

### Phase 4: 等待确认

- 输出计划后**停止**，等待用户反馈
- 用户确认后退出规划模式，按计划逐步执行
- 用户要求修改计划时，更新计划后再次等待确认

## 执行阶段

用户确认计划后：

1. 用 `todo_write` 将计划中的每个 Step 转为 TODO 项
2. 逐步执行，每完成一步标记 `completed`
3. 执行中遇计划外问题，先说明偏差，再继续或等待用户决策
4. 全部完成后，总结变更并验证

## 原则

- **只读不写**：规划阶段禁止使用任何文件修改工具（`string_replace`、`write`、`delete_file` 等）
- **完整阅读**：不要基于假设描述代码，必须先读取文件确认
- **渐进细化**：信息不足时先标注 `[待确认]`，不强编
- **范围控制**：计划中明确"不在本次范围"，防止蔓延
- **一个计划一次确认**：不要在一次确认中塞入过多变更
